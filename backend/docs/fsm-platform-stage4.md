# Этап 4: Outbox и realtime

На этапе 4 в FSM Platform добавляются надёжная доставка внешних вызовов после
фиксации транзакции и отправка актуального состояния клиентам в реальном
времени.

## Работа Outbox

```text
Доменный effect
  -> INSERT в core_outbox внутри транзакции FSM
  -> Worker выполняет COMMIT
  -> OutboxDispatcher захватывает событие и фиксирует захват через COMMIT
  -> HTTP handler выполняется без открытой транзакции БД
  -> новая транзакция переводит событие в SENT, RETRY или FAILED
```

Outbox обеспечивает доставку типа at-least-once: событие будет доставлено как
минимум один раз, но при сбоях возможна повторная отправка. Поэтому каждое
событие обязано иметь `idempotency_key`. При HTTP-вызове этот ключ передаётся в
Core через заголовок `Idempotency-Key`.

Если процесс завершится после успешного HTTP-вызова, но до записи статуса
`SENT`, событие будет отправлено повторно. Core должен распознавать такие
повторы по `Idempotency-Key` и не выполнять одну операцию дважды.

Статусы Outbox:

- `PENDING` — событие ожидает первую отправку;
- `PROCESSING` — событие захвачено одним из dispatcher-процессов;
- `RETRY` — предыдущая отправка завершилась ошибкой, ожидается повтор;
- `SENT` — событие успешно доставлено;
- `FAILED` — исчерпан лимит попыток.

Задержка между попытками увеличивается экспоненциально до установленного
предела. Зависшие события со статусом `PROCESSING` автоматически возвращаются
в `RETRY` либо переводятся в `FAILED`, если лимит попыток уже исчерпан.

Формат HTTP payload:

```json
{
  "method": "POST",
  "path": "/orders/123/performer",
  "body": {"userId": 205, "performer": 1},
  "headers": {}
}
```

## Работа realtime

После успешного выполнения SQL Core и локальных effects Runtime записывает
событие `fsm.transition` в таблицу `realtime_events`. Запись выполняется в той
же транзакции, что и переход FSM. Поэтому отменённые через rollback переходы
никогда не попадут клиентам.

Realtime API читает зафиксированные события, публикует их через `RealtimeHub`,
а затем переводит в статус `PUBLISHED`. WebSocket-клиент получает не только
внутреннее событие FSM, но и актуальный доменный snapshot, построенный с учётом
пользователя. В snapshot также входят доступные ему действия
`availableActions`. Роль и идентификатор берутся только из
аутентифицированного `Principal`, а доступ к сущности проверяется доменной
access policy.

Доступные endpoints:

```text
GET /api/realtime/snapshot/{service}/{entity_type}/{entity_id}
GET /api/realtime/events/{service}/{entity_type}/{entity_id}?after=0&limit=100
WS  /api/realtime/ws/{service}/{entity_type}/{entity_id}
```

WebSocket отправляет сообщения следующих типов:

```json
{"type": "snapshot", "snapshot": {}}
{"type": "entity.updated", "event": {}, "snapshot": {}}
{"type": "ping"}
```

Endpoint истории событий позволяет восстановить пропущенные события по
`eventId`. Для этого клиент передаёт идентификатор последнего полученного
события в параметре `after`.

Для одного процесса используется `InMemoryRealtimeHub`. Для нескольких
процессов или серверов реализован `RedisRealtimeHub`, который распространяет
события между всеми экземплярами API. Таблица событий в БД остаётся источником
данных для восстановления пропущенных событий.

## Установка

Сначала необходимо применить миграции предыдущих этапов, затем выполнить:

```text
fsm_core/sql/005_outbox_realtime.sql
```

Миграцию можно запускать повторно. Она также обновляет раннюю заготовку таблицы
`core_outbox`, которая была добавлена вместе с Taxi-слоем.

## Запуск процессов

FSM Worker:

```bash
python fsm_worker.py
```

Worker доставки запросов в Core:

```bash
CORE_API_URL=https://core.example.test python outbox_worker.py
```

Domain API для snapshot, истории событий и WebSocket:

```bash
uvicorn fsm_api:app --host 0.0.0.0 --port 8001
```

Подключение к БД настраивается существующими переменными окружения:

```text
DB_HOST
DB_PORT
DB_NAME
DB_USER
DB_PASSWORD
```

Токен Core API при необходимости передаётся через `CORE_API_TOKEN`.

Realtime backend выбирается через `FSM_REALTIME_BACKEND=memory|redis`. Для
Redis также задаётся `FSM_REDIS_URL`.

Domain API не доверяет `role` из URL. Для встроенной MVP-аутентификации можно
передать серверный JSON ключей через `FSM_API_KEYS_JSON`. В рабочем окружении
внешний auth middleware может передать уже проверенный `Principal`.

## Границы ответственности

- Worker остаётся единственным владельцем доменной транзакции и выполняет
  `COMMIT` или `ROLLBACK`.
- Outbox handler не получает SQLAlchemy Session и не выполняется внутри
  транзакции захвата события.
- Runtime записывает только универсальные события переходов и не содержит
  бизнес-правил Taxi или Courier.
- Snapshot builders и вычисление `availableActions` находятся внутри доменных
  пакетов.
- Snapshot, replay и WebSocket требуют аутентифицированный `Principal` и
  успешную доменную проверку доступа к сущности.
- Snapshot builders выполняются через read-only Session и не имеют права
  изменять данные или управлять транзакцией.
- `TaxiOrderActions` всё ещё содержит старые синхронные вызовы Core. Это
  временный мост миграции, а не целевой путь этапа 4. Новые Runtime effects
  должны записывать запросы через `write_core_outbox`. Точные пути и payload
  Core необходимо утвердить до отключения старого слоя.
- Полноценный Timer Runtime не входит в этап 4.

## Гарантии и ограничения

В текущей реализации гарантируется:

- атомарная запись состояния FSM и realtime-события;
- отсутствие внешних HTTP-вызовов внутри доменной транзакции;
- повторная доставка Outbox после временной ошибки;
- защита внешних операций через `Idempotency-Key`;
- восстановление зависших Outbox и realtime-задач;
- отправка актуального snapshot после изменения состояния;
- получение пропущенных событий через replay endpoint.

Для завершения интеграции с рабочим окружением остаётся настроить:

- реальный адрес Core API;
- авторизацию Core API;
- точные пути и payload операций Core;
- рабочий источник Principal или набор API keys;
- Redis при запуске нескольких экземпляров Domain API.
