# Platform Core — дорожная карта

Шесть этапов от «одно действие карты ходит через контракт» до полноценного runtime.
Каждый следующий этап начинается только после того, как предыдущий сдан и
функционально эквивалентен состоянию до него.

Сквозное правило: **любая итерация не меняет наблюдаемое поведение приложения**.
Меняется путь, по которому идёт действие, а не результат. См.
[«Архитектурные инварианты»](ARCHITECTURE.md#архитектурные-инварианты).

---

## Stage 1 — Minimum Viable Integration ✅ сделано

Одно пользовательское действие карты проведено через Interaction Contract.

**Что есть:**

| Компонент | Файл |
|---|---|
| Контракт (внешний пакет, без правок) | `src/platform/interaction-contract/` |
| Протокол канала: типы Action/Event + `IApplicationContract` | `map-channel/map-channel-protocol.ts` |
| In-memory реализация шины | `map-channel/AppInteractionContract.ts` |
| Чистый Mapper | `map-channel/MapMapper.ts` |
| Транспорт и логи границы | `map-channel/MapChannel.ts` |
| Прикладной обработчик | `map-channel/MapApplicationHandler.ts` |
| Логгер границы | `map-channel/logger.ts` |
| React-адаптер + UI-подписчик | `map-channel/useMapChannel.ts` |
| Юнит-тесты | `map-channel/__tests__/` |

**Цепочка:**

```
тап по заказу → MapChannel.selectOrder → MapMapper → Action driver.order.select
   → AppInteractionContract.dispatch → MapApplicationHandler (валидация + publish)
   → Event driver.order.selected → UI-подписчик → если !mockEnabled → setOrderCardModal
```

**Критерий сдачи (выполнен):** тап по заказу порождает пару Action/Event на обоих
путях рендера; поведение карты, тайминг и формат логов не изменились; правила шины
зафиксированы юнит-тестами.

## Stage 2 — Platform Interface ✅ базовая модель реализована

После интеграции Map Channel выделяется Platform Interface как универсальный слой
представления между Platform Core и Platform Channel.

Stage 2 — это не разработка новых Surface как самоцель, а эксперимент по верификации
архитектуры Platform Interface: Simple и HUD выступают испытательными стендами для
проверки того, что схема `Platform Core → Platform Interface → Surface → Platform
Channel` выдерживает расширение без изменения самой себя. Если подключение проходит
без изменений — гипотеза подтверждена. Если нет — это основание для архитектурного
пересмотра PI, а не повод менять Simple или HUD в обход схемы.

На этом этапе вводится понятие Surface — независимой формы пользовательского
представления. Первая версия поддерживает:

- Map;
- HUD;
- List;
- Simple;
- Chat.

Существующий Map Channel подключается к Surface Map. Бизнес-логика, Interaction
Contract и поведение карты не изменяются.

**Перед реализацией:** результаты ревью существующего Platform-слоя и границы
переноса зафиксированы в
[PLATFORM_INTERFACE_REVIEW.md](PLATFORM_INTERFACE_REVIEW.md).

**Критерии приёмки этапа:**

1. Platform Interface выделен как самостоятельный слой архитектуры.
2. Реализована минимальная модель Surface и явная регистрация Surface.
3. Map Channel работает через Surface Map без изменения поведения.
4. Как минимум два новых Surface (Simple и HUD) подключены через существующую
   цепочку `Platform Core → Platform Interface → Surface → Platform Channel` без
   изменения архитектурной диаграммы, архитектурных инвариантов и публичных
   контрактов Platform Core и Platform Interface. Если подключение Simple или HUD
   требует такого изменения, этап не считается завершённым и является основанием
   для пересмотра модели Platform Interface, а не для точечного исключения.
5. Interaction Contract и существующая бизнес-логика не изменены.

Подробная целевая модель — в [SURFACE_MODEL.md](SURFACE_MODEL.md).

**Статус 2026-08-08:** реализованы `Surface`, `SurfaceRegistry`, Map, Simple,
HUD, List и Chat Surface. Добавлен `PlatformInterfaceRuntime`, единый read-only
Snapshot, `availableActions`, Navigation Runtime и внедряемый
`DomainApiSnapshotProvider`. Реальный Domain FSM transport остаётся внешней
зависимостью. Подробности — в
[PLATFORM_INTERFACE_RUNTIME.md](PLATFORM_INTERFACE_RUNTIME.md) и
[PLATFORM_INTERFACE_STAGE3_6_REPORT.md](PLATFORM_INTERFACE_STAGE3_6_REPORT.md).

## Stage 3 — Остальные действия карты через контракт ✅ сделано

Расширение уже работающей границы: карта перестаёт быть источником команд Redux и
становится источником намерений.

**Что переводится** (якоря — `src/pages/Driver/Map.tsx`, полный разбор в
[STATE_AND_API.md](STATE_AND_API.md)):

| Сейчас напрямую | Строка | Кандидат в Action |
|---|---|---|
| `setOrderCardModal` в `onMapStartedClick` | 1152 | `driver.order.card.open` |
| `setMessageModal` при ошибке | 1130 | `driver.order.action.failed` (Event) |
| `getOrder` ×3 после мутации | 1143 / 1158 / 1168 | следствие Event’а, а не команда карты |
| `setRatingModal` после завершения | 1170 | `driver.order.finished` (Event) |
| `getAreasBetweenPoints` | 1439 | `driver.route.areas.requested` |

**Критерии приёмки этапа:**

1. **Большинство действий карты идёт через контракт** — прямые вызовы остаются
   исключением, каждое сохранившееся исключение названо и обосновано.
2. **Новая функциональность добавляется только через Platform Core** — новый Redux-
   диспатч или вызов `API.*` прямо из компонента карты не проходит ревью.
3. **Прямые связи Redux/API из карты сокращены** относительно Stage 1 — счётчик из
   таблицы выше уменьшается измеримо, а не «концептуально».
4. Каждое переведённое действие закрыто юнит-тестом Mapper’а и обработчика.
5. Поведение приложения не изменилось.

**Здесь же появляется Provider** отдельным файлом: на Stage 1 он сознательно не
выделен (событие клика уже инкапсулировано `eventHandlers` маркера), но с ростом
числа источников событий карты инкапсуляция перестаёт быть бесплатной.

**Статус 2026-08-08:** lifecycle, открытие карточки, запрос areas и обработка
результата переведены на Action/Event. Прямых импортов `API.*` в Driver Map нет;
read-запросы геокодинга проходят через адаптер, а ORS → local graph → OSRM
инкапсулирован в Route Provider.

## Stage 4 — Backend Adapter ✅ локальная реализация готова

Сейчас за контрактом стоит in-memory шина, а бэкенд живёт своей жизнью и про Platform
Core не знает. Этап закрывает разрыв: появляется адаптер, который превращает Action в
вызов бэкенда, а ответ — в Event.

**Состав:**

- адаптер `API.*` за границей контракта: карта и другие каналы больше не знают
  ни об `ibronevik`, ни об HERE/Nominatim/OpenRouteService;
- нормализация ошибок бэкенда в `InteractionError` — включая то, что ошибки приходят
  с HTTP 200 и распознаются двумя разными признаками (`status === 'error'` и
  `code !== '200'`);
- мутации жизненного цикла заказа (`setOrderState` Arrived/Started/Finished,
  `arrivedVotingOrder`) как Action’ы с подтверждающими Event’ами.

**Критерий сдачи:** ни один канал не вызывает `API.*` напрямую; отказ бэкенда
доезжает до UI как Event, а не как исключение внутри обработчика клика.

**Риск этапа — самый высокий из всех:** затрагивается состояние на стороне бэкенда.
Нужен отдельный план отката до начала работ.

**Статус 2026-08-08:** `LegacyBackendGateway` является единственной backend-точкой
для UI, ошибки нормализуются и публикуются как Event. Arrive, Start,
Confirm Boarding и Finish оформлены как Action с подтверждающим Event. Замена
legacy transport на серверный Domain FSM остаётся внешней интеграционной задачей,
для которой нужны endpoint, payload, auth и realtime contract.

## Stage 5 — Driver FSM + Snapshot 🟡 частично

Появляется доменное состояние: конечный автомат водителя (свободен → назначен →
подъехал → в пути → завершил) на стороне Application.

**Состав:**

- FSM как единственный владелец переходов; Action проверяется на допустимость
  перехода, недопустимый отклоняется Event’ом, а не молча;
- `snapshot()` наполняется доменным состоянием — до этого этапа он сознательно
  возвращает `{revision, state: {}}`;
- `revision` из snapshot становится основой синхронизации каналов.

**Критерий сдачи:** состояние водителя читается из snapshot, а не собирается по
кускам из Redux; переходы, невозможные по FSM, не выполняются ни одним каналом.

**Статус 2026-08-08:** Driver Snapshot projection реализован и используется HUD и
List/Map. Источником временно служит Redux Provider. Серверная валидация переходов
и серверный FSM как источник истины не могут быть завершены без Domain API.

## Stage 6 — Runtime 🟡 базовый runtime готов

Platform Core становится самостоятельным runtime, а не библиотекой внутри приложения
карты.

**Состав:**

- несколько каналов одновременно (карта, голос, мессенджер) поверх одного ядра;
- жизненный цикл: старт, остановка, восстановление после разрыва;
- наблюдаемость вместо `console.log`: структурные события, корреляция по
  `correlationId` через всю цепочку;
- контракт как внешняя зависимость с версионированием, а не копия в `src/platform/`.

**Критерий сдачи:** новый канал подключается без правок в ядре и в существующих
каналах.

**Статус 2026-08-08:** lifecycle Surface, Navigation Runtime, сменяемый Snapshot
Provider, reconnect/backoff и корреляция Action/Event реализованы. Добавлен
реальный Query/WebSocket transport для одного известного taxi/order. Полный
Driver Runtime остаётся незавершённым до появления серверных Command API, Driver
Snapshot и браузерно-совместимой WebSocket-авторизации. Внешний версионированный
контракт и одновременная работа независимых процессов остаются следующими шагами.

## Ограничения Stage 1 (исторический baseline)

Пункты ниже описывают состояние на момент завершения Stage 1. Актуальный статус
Stage 3–6 приведён выше; прямые UI-вызовы backend и пустой Snapshot уже устранены
локальными адаптерами и Provider.

Честный список того, чего на текущем этапе **нет**. Ни один пункт не является
дефектом — это осознанно отложенный объём.

**Backend не знает про Platform Core.**
Контракт заканчивается in-memory шиной внутри вкладки браузера. Все запросы к
`ibronevik`, HERE, Nominatim и OpenRouteService идут мимо него, как и до интеграции.
Закрывается на Stage 4.

**FSM нет.**
Доменных переходов и их валидации не существует; Application-обработчик проверяет
только форму Action’а (тип и непустой `orderId`), но не допустимость действия в
текущем состоянии водителя. Закрывается на Stage 5.

**Контракт локальный.**
`src/platform/interaction-contract/` — копия upstream внутри репозитория, а не
внешняя зависимость. Сверка целостности — ручная (md5 при переносе), автоматической
проверки в CI нет. Шина живёт в памяти одной вкладки: ни межпроцессного транспорта,
ни сериализации на проводе. Закрывается на Stage 6.

**Snapshot не используется.**
`snapshot()` возвращает `{revision, state: {}}` — структура доменного состояния
контракту неизвестна по определению, а наполнять его нечем, пока через границу идут
только действия. Метод не бросает исключений и безопасен к вызову, но полезной
информации не несёт. Закрывается на Stage 5.

**Через контракт идёт одно действие.**
`driver.order.select` — и ничего больше. Пять props-диспатчей и четыре вызова `API.*`
из карты остаются прямыми. Закрывается на Stage 3.

**Provider отдельным файлом не выделен.**
Событие клика уже инкапсулировано `eventHandlers` маркера react-leaflet и колбэком
`onMarkerClick` кластерного слоя; отдельный слой на одном действии был бы пустой
абстракцией. Закрывается на Stage 3.
