# 12. Способы заказа и защита submit

## Основание

31.10 10:27 — дублирование кнопок; 10:31 — Vote недоступен между городами. Ранее: Vote означает «еду на первом прибывшем такси».

## Требования

- Главная часть каждой кнопки отправляет соответствующий запрос. Отдельный «?» открывает только объяснение и возвращает фокус при закрытии.
- Offer сначала открывает сумму; подтверждение использует тот же validated submit. Нулевая/нечисловая цена блокируется существующей валидацией.
- Междугородний и отложенный более чем на 15 минут заказ не допускает немедленный Vote. Другие ограничения не выдумываем без контракта.
- Единственный resolver разрешённых режимов используется и layout, и чтением текущего store перед отправкой. Смена маршрута не оставляет доступным старый Vote.
- Передать effectiveLocationClass с учётом ручного override вместо безусловного algorithmLocationClass.
- Сохранить createOrder payload, верификацию Offer, pending lock и существующую FSM.

## Приёмка

1. Город сейчас: три прямых действия; нажатие «?» не создаёт заказа.
2. Межгород/позже: Vote отсутствует во всех layout; вызов submit('vote') отклоняется до API.
3. Offer: ввод суммы без автоматической отправки; подтверждение один раз. Cancel/Escape не отправляют.
4. Непроверенные зоны/ожидание запроса блокируют команды, справка остаётся доступной.
5. Смена маршрута при открытой подсказке недопустимого режима закрывает её.
6. Язык и подписи поступают из ключей БД (ТЗ 11).
