# Принятая команда: восстановление после перезагрузки

Изменение сделано в отдельном frontend. Исходный репозиторий и рабочий backend не изменены.

## Поведение

После ответа Command API с `instanceId` приложение сохраняет идентификатор команды, заказ, тип действия и время принятия. Запись связана с текущими водителем, сервисом и конкретным входом. PIN, токены и тело команды в этот журнал не попадают.

После reload выполняется только чтение `GET /api/commands/{instanceId}`. Повторного POST нет. Пока результат неизвестен, следующая команда для этого заказа запрещена. Другие заказы доступны.

Ошибка чтения, потеря связи и таймаут не означают отказ выполнения. Водитель видит «Проверить результат». Эта кнопка повторяет только чтение статуса. После подтверждённого результата перечитывается заказ и выбранный источник данных интерфейса; сохранённая запись сама не переводит поездку в Started или Finished.

Успешный результат и подтверждённый отказ показаны разными сообщениями. После смены аккаунта старые ответы не обновляют новую сессию. Если браузер не разрешил сохранение, появляется предупреждение не закрывать страницу.

Legacy-режим не объявляется FSM: без Command Status API журнал не включается. Проверка снимка заказа сама по себе не считается доказательством результата конкретной принятой команды.

## Дополнительно найдено при регрессии

В первом прогоне Offer уведомление о принятом предложении повторно открылось после reload и перекрыло выезд на карте. Источниками были список, карточка и страница заказа. Для одного заказа в одной сессии уведомление теперь показывается один раз. Отправка предложения, назначение водителя и цена не менялись.

## Воспроизводимые проверки

1. Jest: `DriverCommandRecovery.test.js`, `DriverMapGateway.test.js`, `sessionTokens.test.js`, `DriverCommandRecoveryNotice/index.test.jsx`, `driverOfferNotifications.test.ts`.
2. Собрать отдельную страницу протокольного теста через `tools/build-cjm.cjs`: `QA_ENTRY=src/qa/command-recovery-entry.tsx`, `QA_OUTPUT_DIR=/tmp/taxi-command-recovery-qa/fixture`, `QA_ROUTE=/`, `QA_CONNECT_POLICY=self`, `NODE_OPTIONS=--openssl-legacy-provider`.
3. Выполнить `node tools/test-command-recovery-browser.cjs`. Тест сам поднимает HTTP fixture на случайном порту только `127.0.0.1`. На рабочий API он не обращается.
4. Браузер физически перезагружает страницу после принятия команды. Проверяются один POST, чтение прежнего instance, отсутствие ложного успеха при отказе, повтор чтения после 403 и размеры 320×568, 390×844, 844×390, 1440×900.
5. Отдельно прогнать три бизнес-сценария на локальном PHP-стенде с настоящими UI-кнопками и независимым чтением результата API. Протокольный fixture не заменяет эту проверку.

## Что ещё требуется от сервера

- На принятом FSM-стенде проверить права пользователя на каждый instance, сохранение конечного результата после перезапуска и срок доступности результата. Команда чужого водителя должна быть недоступна.
- Утвердить поведение, если POST ушёл, но ответ с `instanceId` потерян. Нужны серверная идемпотентность и поиск команды по клиентскому `commandId`/ключу. Этот журнал начинается после получения instance и не закрывает потерю ответа до принятия.
- Подключить пользовательскую авторизацию FSM. Общий секрет в браузерной сборке запрещён.

Проверка настоящего FSM, физических телефонов и нагрузки 200–400 водителей остаётся отдельной приёмкой. Локальные результаты не доказывают готовность рабочего сервера к пилоту.
