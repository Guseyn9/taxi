README и автоматических тестов в полученном дереве нет. Код изучен статически; сервер и SQL-дампы не запускались, данные рабочего сервиса не менялись.

Это FastAPI/MySQL-прототип логистики с посылками, постаматами и рейсами. Он не является готовой заменой текущего taxi API: заказ (`order`) и рейс (`trip`) разделены, модели содержат города/ячейки, а не текущие `b_*`, координаты, цену/валюту, кандидатов и PIN такси.

- `main.py:528–560`: `POST /api/fsm/action` принимает `entity_type`, `entity_id`, `action_name`, **user_id из тела**; `GET /api/fsm/buttons` принимает **user_role из query**. В этих обработчиках видна только зависимость БД, проверки аутентифицированного пользователя нет. Это наблюдение об исходнике, не утверждение о конфигурации неизвестного размещённого сервера.
- `models.py:20–25,71–78`: ответ команды — `success/message/data`, кнопки — `button_name/is_enabled`. Это другой envelope, чем `code/status/data` действующего PHP API. Snapshot/version/command ID в этих моделях отсутствуют.
- `db_layer.py:79–117`: действие вызывает SQL-процедуру `fsm_perform_action` и делает commit. Рядом остаются прямые UPDATE stage-таблиц. Само наличие FSM endpoint не означает, что все переходы переведены на FSM.
- `main.py`: доступны создание пользователей, обработка таймаутов и `POST /api/test/clear`; такие административные/разрушающие операции не должны быть доступны обычному браузерному клиенту.

## Как закончить рефакторинг

1. **Зафиксировать предметную модель с автором.** Уточнить, является ли репозиторий актуальным taxi FSM или отдельной логистической веткой. Получить актуальную схему/миграции/таблицу переходов; сопоставить `order/trip` с booking/driver participation. Не назначать эти сущности эквивалентными по названию.
2. **Сначала серверный контракт и ACL.** Пользователя и роль получать из проверенной сессии, а не доверять user_id/user_role клиента. Сервис/tenant, владение заказом, роль и допустимый переход проверять атомарно на сервере. Таймауты и test/clear вынести в административный контур.
3. **Сделать команду проверяемой.** Request: command ID/idempotency key, entity ID, ожидаемая версия, action, согласованные данные. Response: command ID, outcome, новая версия и canonical snapshot либо handle для readback. Повтор того же command ID возвращает тот же результат; конфликт версии не перезаписывает чужое действие. Commit, запись результата команды и переход должны быть одной транзакцией.
4. **Убрать обходы FSM по одному переходу.** Создание → приглашение/оффер/голосование → выбор → take/arrive → PIN/start → завершение/отмена. Для каждого перехода согласовать входы, владельца и терминальные состояния. Сохранить цены/валюту, GPS, отмену и settlement. Прямые записи состояния после перехода не оставлять параллельным источником истины.
5. **Подключать через существующие границы фронта.** В проекте уже есть `LegacyPassengerGateway`, `DriverMapGateway`, interaction-contract, command completion/recovery, query/polling и Passenger presentation. Новый транспорт реализовать за этими границами; компоненты не должны напрямую вызывать `/api/fsm/action` и самостоятельно вычислять серверное состояние. UI FSM отображения и серверная FSM жизненного цикла имеют разные задачи.
6. **Проверить адаптеры и включать по tenant/feature flag.** Contract tests обоих envelope; недоступная команда, чужой/неверный/replayed PIN, ACL, два клиента одновременно, timeout после commit, restart/readback, stale version и смена сессии. Затем парный пассажир/водитель на тестовом tenant, reconnect и физические устройства. Не выполнять dual write в оба API. Rollback переключает транспорт, сохраняя серверный ID и завершённые команды.

На текущем этапе безопасно сохранить рабочий legacy transport и подготовленные границы. Просто заменить URL на этот FastAPI и перевести названия кнопок в action_name недостаточно.

## MCP

[iriswolf/ibronevik-taxi-mcp](https://github.com/iriswolf/ibronevik-taxi-mcp) 08.11 недоступен текущему GitHub-подключению: запрос метаданных и contents вернул 404. Это может означать приватный репозиторий или отсутствие доступа; утверждать, что репозитория не существует, нельзя. Внешнее открытие URL тоже не дало исходник. Установки, запуска и административных вызовов не было.

Чтобы освоить именно этот MCP, нужны доступный исходник с зафиксированной версией и документация текущих инструментов. До этого нельзя подтвердить его команды, авторизацию или готовность server mode. Предлагаемый порядок после получения доступа:

1. Проверить read/write инструменты, обработку tenant, credential storage, журнал и доступность произвольных API/SQL-команд. Выделить read-only роль и allowlist разрешённых методов.
2. Разместить server mode на доверенном сервере: TLS, аутентификация агента, tenant-scoped credentials, таймауты/лимиты, редактирование секретов в логах. Админские токены остаются на сервере; в bundle React их нет.
3. Начать с чтения health/конфигурации/констант на согласованном dev tenant. Проверить запрет чужого tenant и админских изменений read-only ролью.
4. Подготовить diff констант и отдельный план активации тестового водителя, проверить права и только затем выполнять разрешённые владельцем административные действия. Инструменты не дают себе разрешение самим фактом доступности.

## Что нужно для реальной пары и настроек Марокко

Ограничение пользователя — frontend, доступа к backend нет. Сообщение Валентина «при получении учётки админа» не содержит саму учётку и не меняет это ограничение. Не хватает:

- согласованного доступа администратора dev tenant или подключённого MCP с нужной ролью;
- согласованных значений констант Марокко: страна/валюта/телефон/зоны и тарифы, включая допустимость варианта «Любой»;
- управляемых тестовых пассажира и водителя, подтверждения контактов, одобренной машины и активации водителя;
- пары физических устройств для исходного crash-сценария, GPS/background и одновременной поездки.

План приёмки после получения условий: пассажир создаёт один заказ → водитель видит его в правильном tenant → take → arrive → проверка неверного/чужого/повторного PIN → правильный start → движение GPS → complete → цена/валюта/отзыв. Отдельно Offer и Voting, отказ/отмена, потеря ответа после записи, фон/возврат, вход с другой учёткой. Сохранять ID команд/заказа и обезличенные логи; не выдавать browser fixtures за такой прогон.

До этого frontend показывает реальные значения конфигурации (в наблюдаемом gruzvill были GHS/GHA/+233 при service_country=ma); не рисует MAD/+212 поверх несогласованного backend.
