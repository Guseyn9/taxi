4 ноября 2026. Решение принимает Валентин, по указанию Макса.

Этот документ заменяет прежнюю рекомендацию считать Universal API основным
вариантом по умолчанию. Подготовлены два пути с отдельной приёмкой. Пока выбор

ВАРИАНТ A — UNIVERSAL API В ПЕРВОМ ПИЛОТЕ

Состав:
— HTTP API /taxi_dev2/c/<tenant>/api/v1, совместимый alias api_test;
— согласованный словарь /taxi_dev2/cache/data_<tenant>.js;
— Standard, Voting и Offer через действующие Universal-команды;
— отдельная последующая миграция на FSM, если её выберут позднее.

Что подготовлено локально:
— совместимые поля offer_mode, driver_offer_eta/driver_offer_comment;
— миграция разрешённых options с dry run, совместимый frontend и контракты;
— профиль/вход/PIN, регистрационная граница, хранение пароля, отзыв credential;
— поддерживаемый кандидат PHP 8.5.12 и PHPMailer 7.1.1;
— реальные локальные HTTP/SQL и браузерные сценарии на присланном backend.
Конкретные результаты и границы каждого прогона — в evidence пакета.

Что выполнить до включения пилота:
1. Сравнить установленный backend с manifest; перенести изменения по смыслу,
   сохранить текущие серверные исправления и проверить backup/restore.
2. Принять backend+миграцию+словарь+frontend одним согласованным комплектом.
3. Пройти серверную матрицу доступа, независимые сессии/TTL и безопасный reset.
4. Реализовать и проверить серверную идемпотентность и атомарность назначения,
   PIN/start/cancel/finish и финансового результата, включая гонки двух ролей.
5. Принять настоящие тарифы, валюту, округление, лицензии/полигоны и время.
6. Пройти реальные интеграции, устройства, нагрузку и эксплуатационные gates.

Сборка A:
REACT_APP_API_ROOT=https://ibronevik.itest24.com/taxi_dev2
REACT_APP_DICTIONARY_ROOT=https://ibronevik.itest24.com/taxi_dev2/cache
REACT_APP_SERVICE_CONFIG=<подтверждённый tenant>
REACT_APP_ALLOWED_SERVICE_CONFIGS=<тот же tenant>
REACT_APP_FSM_API_URL не задавать.
Проверить реальные Network-запросы и словарь после сборки.

Приёмка A:
— все сценарии E2E выполняются против реального Universal API общего dev;
— не теряются смены статуса/суммы после timeout, reload, reconnect и logout;
— повтор одной операции не создаёт второе назначение/поездку/списание;
— server-side ограничения нельзя обойти прямым HTTP-запросом;
— известны commits, tenant, schema/migration, dictionary и rollback-комплект.
Срок A оценивается после сверки установленного сервера и остатка общих gates.

ВАРИАНТ B — НОВЫЙ FSM УЖЕ В ПЕРВОМ ПИЛОТЕ

Состав:
— пользовательская авторизация серверных Query/Command/Status/WS;
— один источник истины для состояния поездки и водителя;
— принятие команды отдельно от её исполнения;
— восстановление неопределённого результата и пропущенных realtime событий.

Что подготовлено локально на frontend:
FsmTaxiCommandTransport, FsmCommandStatusTransport, FsmOrderSnapshotTransport,
FsmDriverSnapshotTransport, DriverCommandCompletionWaiter и DriverCommandRecovery.
Есть тесты протокола, completion, reconnect, polling и восстановления принятого
instanceId после reload. Они используют управляемые ответы транспорта и не
доказывают существование соответствующего сервера или его авторизации.

Ожидаемые frontend endpoints — предмет сверки с настоящим FSM, не утверждение
о реализации на taxi_dev2:
POST /api/commands/taxi/order/{orderId}
GET  /api/commands/{instanceId}
GET  /api/realtime/snapshot/taxi/order/{orderId}
GET  /api/realtime/snapshot/taxi/driver/{driverUserId}
WS   /api/realtime/ws/taxi/order/{orderId}
WS   /api/realtime/ws/taxi/driver/{driverUserId}

Command сейчас отправляет schemaVersion=1.0, commandId, correlationId, intent,
payload и заголовок Idempotency-Key. Новый ответ ожидается как HTTP 202,
accepted=true, duplicate=false, положительный instanceId, status и intent.
Дубль — HTTP 200, accepted=true, duplicate=true с прежним instanceId.
Status знает PENDING/PROCESSING/COMPLETED/FAILED. HTTP 202 не переводит UI
самостоятельно в выполненное состояние; завершение сверяется с новым Query.
Точные схемы snapshots/events и intents сверить по исходникам adapters и
зафиксировать в версионированном серверном контракте до реализации интеграции.

Серверная работа B:
1. Валентин предоставляет действующий репозиторий/версию FSM, схемы и примеры
   обезличенных ответов. Если сервер отсутствует, это отдельная реализация,
   которой нет в присланном PHP-архиве. Не подменять её mock-сервисом для приёмки.
2. Принять пользовательскую сессию и серверную проверку tenant/user/order на
   каждом Query, Command, Status и WS-подключении/подписке. Status instanceId
   не должен раскрывать чужую команду. Отзыв сессии прекращает доступ и WS.
3. Убрать использование общего REACT_APP_FSM_API_TOKEN из production-сборки:
   существующая опция транспорта не является готовой пользовательской auth.
   Выбрать серверный BFF/сессионный механизм, CSRF/CORS и безопасный WS-handshake;
   долгоживущий bearer в query URL не использовать. После этого доработать
   транспорта frontend под утверждённый механизм и проверить смену аккаунта.
4. Реализовать durable command journal/outbox, хранение idempotency и атомарный
   переход. Один ключ и тот же payload возвращают тот же результат; другой
   payload с тем же ключом отклоняется. Повтор после timeout не исполняет write
   второй раз. Для потерянного до Accepted ответа нужен поиск по commandId;
   одного известного instanceId недостаточно.
5. Принять конечные статусы, retryable/terminal ошибки, дедлайны, Retry-After,
   retention и восстановление команд после перезапуска worker/сервера.
6. Snapshots: монотонная revision, актуальные availableActions и полный Query
   после пропуска WS. Старое/дублированное событие не откатывает состояние.
7. Связать реальные orderId/driverUserId с текущим пользователем и выбранной
   поездкой; не использовать фиксированный REACT_APP_FSM_ORDER_ID как решение
   для всех заказов. Сверить mapping backend states/modes с Universal-данными.
8. Проверить все команды обоих участников, а не только водителя: создание,
   отклик/предложение, выбор, отказ, подача, PIN/start, отмена/SOS, finish,
   оценки и финансовый результат. Переходы и права — на сервере.

Сборка и приёмка B:
— REACT_APP_FSM_API_URL указывает на принятый FSM/BFF; общего токена в JS нет;
— выбран один согласованный набор Query/Command/Status/WS, словарь и tenant;
— существующие E2E привязываются к реальному FSM и проверяют серверный результат;
  зелёный Universal-прогон или unit mocks не засчитываются как приёмка B;
— сценарии A плюс 202 без выполнения, terminal failure, timeout до/после commit,
  потерянный Accepted, duplicate key, падение worker, reload/unmount, потери и
  перестановка WS, 401/403/429, другой аккаунт/tenant/instanceId;
— восстановление выполняет чтение, не слепой повтор POST; после неизвестного
  результата нельзя автоматически переключиться на legacy write;
— нагрузка учитывает реальный Query/polling/WS профиль и reconnect storm.
Срок B включает backend и пользовательскую auth, сверку схем и повторную
интеграционную приёмку. Его нельзя получить переключением env-переменной.

ОБЩИЕ УСЛОВИЯ ПРОДА И ПОРЯДОК РЕШЕНИЯ

Для A и B одинаково обязательны закрытие согласованных security-задач,
серверная денежная модель, регион и лицензии, реальная доставка/платежи
включённого объёма, время/отложенные поездки/DST, физические устройства,
нагрузка 200/400 водителей, обязательные CI checks, безопасные отчёты,
мониторинг/алерты, поддержка, backup/restore, совместимый rollback и пилот.

До общего dev зафиксировать: вариант A или B, включённые режимы и интеграции,
tenant/URL/commits/schema/dictionary, механизм auth и владелец каждого gate.
Если B требует временного смешанного режима, отдельно утвердить владельца
каждого чтения и каждой команды, связь IDs и миграцию. Смешанный режим не
считается автоматически готовым третьим вариантом.

Валентин принимает решение по варианту и серверному контракту. Администратор
выполняет доступные только ему операции. Наша сторона переносит согласованные
изменения frontend/контрактных тестов и фиксирует проверяемый release-кандидат.
