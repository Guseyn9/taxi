# TEST-E2E-001 — посадка по коду в голосовом заказе

Playwright-прогон полного пользовательского сценария против **живого backend**
(`https://ibronevik.ru/taxi/c/gruzvill/api/v1`). Закрывает дефект
ТЗ-DRIVER-BOARDING-001: после подтверждения кода посадки бэкенд переводил заказ
в `Started`, а интерфейс водителя оставался в режиме «Код посадки».

## Запуск

```bash
cd taxi
npm run test:e2e            # все тесты
npm run test:e2e -- -g "A:" # один
npm run test:e2e:report     # HTML-отчёт последнего прогона
```

Dev-сервер Playwright поднимает сам (`npm start`). Если он уже запущен —
переиспользует; чтобы указать другой адрес, задайте `E2E_APP_URL`.

Первый запуск требует браузера: `npx playwright install chromium`.

## Учётные данные

Тест работает с настоящими учётками — в репозиторий они не попадают. Создайте
`taxi/.env.e2e.local` (он в `.gitignore`) или задайте переменные окружения:

```
E2E_DRIVER_LOGIN=...
E2E_DRIVER_PASSWORD=...
E2E_DRIVER_TYPE=e-mail
E2E_PASSENGER_LOGIN=...
E2E_PASSENGER_PASSWORD=...
E2E_PASSENGER_TYPE=e-mail
E2E_API_BASE=https://ibronevik.ru/taxi/c/gruzvill/api/v1
```

Подойдут те же тестовые аккаунты gruzvill, которыми пользуется
`driver-emulator` (`driver-emulator/config.json`): водитель из `drivers[]` и
пассажир из `orderGenerator.clients[]`. У водителя должна быть привязанная
машина — из неё берётся код посадки.

## Что настоящее, а что нет

Настоящее: frontend, Taxi API, состояние заказа, переходы, обе роли.
**Ни один endpoint сценария не подменяется** — ни создание заказа, ни
`set_performer`, ни `set_arrive_state`, ни `set_start_state`.

Единственный мок — тайлы карты (внешний тайловый сервер к посадке отношения не
имеет, §4 ТЗ).

Что делает браузер: смотрит заказ, откликается, едет, отмечает прибытие, вводит
код и подтверждает. Что делает тест напрямую через API: готовит данные
(пассажир создаёт голосовой заказ и выбирает водителя) и **независимо** от UI
читает состояние заказа для проверок. Redux из теста не трогается, шлюз не
вызывается, backend-команды вместо клика не отправляются.

`?driverEmulator=1` в адресе — штатный переключатель приложения
(`tools/emulatorMode.ts`), без него список заказов водителя принудительно пуст.
Это режим приложения, а не мок API.

## Тесты

| Тест | Что проверяет |
|---|---|
| A | правильный код → backend `Started`, интерфейс `Started`, форма посадки закрылась |
| B | код неверной формы → команда не уходит, заказ остаётся `Arrived`, интерфейс в режиме посадки |
| C | двойное нажатие «Подтвердить» → одно корректное итоговое состояние |
| D | перезагрузка страницы → интерфейс всё ещё `Started`, подтверждение кода не вернулось |

Состояние интерфейса читается атрибутом `data-driver-state` кнопки основного
действия, а не переводом подписи: подписи приходят из конфигурации бэкенда и
зависят от языка, состояние — нет.

## Почему в тесте A есть верхняя граница по времени

Дефект был не в том, что интерфейс **никогда** не догонит бэкенд, а в том, что
он догонял его только следующим опросом списка заказов. Первая версия теста без
границы **проходила на сломанном коде** — это проверено инъекцией регрессии.

Поэтому тест A замеряет, за сколько интерфейс приходит в `Started`, и требует
уложиться в `UI_SYNC_BUDGET_MS` (1.5 с) — заведомо меньше периода опроса
активных заказов (5 с) и отложенного refresh (1.5 с). Уложиться можно только за
счёт локальной синхронизации.

Проверка инъекцией регрессии (полный откат исправления — синхронизация store в
карточке, оптимистичное состояние карты и отметка подтверждённой посадки):

```
Expected: 5   (Started)
Received: 4   (Arrived)
```

То есть тест ловит ровно ту картину, что описана в ТЗ: `Backend = Started`,
`UI = Arrived`.

Откат **только** карточной синхронизации или **только** механизмов карты тест не
ловит — оставшегося пути хватает, чтобы уложиться в бюджет. Точечно каждый
механизм сторожат unit-тесты (`driverBoarding.test.ts`,
`DriverBoardingProjection.test.js`, `driverOrderState.test.ts`).

## Что выяснилось про backend (важно для §16 ТЗ)

На конфигурации `gruzvill`:

1. **Код посадки бэкендом не проверяется.** `set_start_state` с заведомо
   неверным `b_driver_code` возвращает `success` и переводит водителя в
   `c_state = 5`. Проверено напрямую по API.
2. **`b_driver_code` в заказе не возвращается.** Приложение сверяет введённый
   код с `order.b_driver_code` (`tools/driverBoarding.ts`), и когда его нет —
   принимает любой код правильной формы (3–4 цифры).
3. Передача `b_driver_code` в `set_performer` отклоняется («wrong driver code»),
   что совпадает с комментарием в `src/API/order.ts` и безопасным ретраем там же.

Поэтому требование ТЗ «неверный код → `Command = FAILED`, `Backend ≠ Started`»
на этом бэкенде невыполнимо: отвергнуть можно только код неверной **формы**, и
делает это фронтенд. Тест B проверяет ровно эту, настоящую гарантию — и не
имитирует недостающую серверную проверку моками. Валидацию кода на сервере
стоит завести отдельной задачей.

## Артефакты при падении

`trace`, `screenshot`, `video` — в `e2e-results/artifacts/`, HTML-отчёт в
`playwright-report/`. Оба каталога в `.gitignore`.

## Изоляция

Каждый прогон создаёт свой заказ, помеченный `[DRV:<id>]` — механизм самого
приложения, по которому водитель в режиме внешнего эмулятора видит только свои
тестовые заказы. После теста заказ отменяется (`afterEach`), аккаунты не
зависают.

Тесты идут строго по одному (`workers: 1`): они делят одного тестового водителя
и его машину.

## CI

`.github/workflows/e2e.yml` — job **Playwright E2E**, запускается на каждый
Pull Request и на push в `main`. Он выполняет ровно ту же команду, что и
разработчик локально:

```
GitHub Actions → npm ci → playwright install chromium → npm run test:e2e
                                                              │
                                              npm start (localhost:3000)
                                                              │
                                          живой backend gruzvill
```

Отдельной CI-реализации сценария нет: один тестовый код, два способа запуска.
`workers: 1`, `retries: 1` и сбор артефактов приходят из `playwright.config.ts`
по переменной `CI`, которую GitHub выставляет сам, — в workflow они не
дублируются.

### Секреты

Учётные данные в CI берутся только из GitHub Secrets репозитория (Settings →
Secrets and variables → Actions). Ключи те же, что в `taxi/.env.e2e.local`:

```
E2E_DRIVER_LOGIN      E2E_PASSENGER_LOGIN      E2E_API_BASE
E2E_DRIVER_PASSWORD   E2E_PASSENGER_PASSWORD
E2E_DRIVER_TYPE       E2E_PASSENGER_TYPE
```

Аккаунты должны быть **тестовыми**: прогон создаёт настоящие заказы. В коде и в
workflow нет ни одного значения — только `process.env.*`.

PR из форка секретов не получает: там тест упадёт с понятным сообщением из
`fixtures/accounts.ts`. Это не маскируется — `continue-on-error` в workflow нет.

### Очередь

Прогоны выстроены в общую очередь (`concurrency`, без отмены текущего): тесты
делят одного тестового водителя и его машину, и два параллельных прогона ломали
бы состояние заказа друг другу.

### Артефакты и диагностика

Артефакты выгружаются всегда (`playwright-e2e-<run>-<attempt>`, 7 дней):
`taxi/playwright-report/` и `taxi/e2e-results/`. Выгрузка на любом исходе нужна
для §15 ТЗ: если первая попытка упала, а вторая прошла, это должно быть видно в
отчёте, а не спрятано за retry.

При падении в лог job уходит строка `E2E FAILURE DIAGNOSTICS` с `orderId`,
`driverId`, `carId` и состоянием заказа на бэкенде. Если отменить заказ не
удалось — `E2E CLEANUP FAILED: orderId=…`: по этому номеру заказ можно найти и
удалить руками. Токены, пароли и cookie в диагностику не попадают.

`taxi/e2e/.auth/` (там storageState с токеном сессии) в артефакты не выгружается.
Проект `setup` идёт вообще без trace/video/screenshot: он вводит логин и пароль в
форму приложения, а trace хранит само значение `fill()`.

Одного этого мало: к любому упавшему тесту Playwright безусловно прикладывает
`error-context.md` — ARIA-снимок страницы, в котором **и логин, и пароль видны
открытым текстом** (проверено инъекцией падения после ввода). Настройкой это не
отключается, поэтому у `setup` вложение снимает репортёр
`e2e/reporters/stripSetupErrorContext.ts`: он стоит первым в списке, поэтому копия
не доходит ни до HTML-, ни до JSON-отчёта, а файл удаляется с диска. Сообщение об
ошибке и стек при этом остаются целиком. Проверка: сломать селектор кнопки входа в
`auth.setup.ts`, прогнать `npx playwright test --project=setup` и поискать значения
учёток в `e2e-results/` и `playwright-report/` — совпадений быть не должно.

Trace самого сценария содержит сетевой обмен приложения, включая токен сессии
тестового водителя, — поэтому срок хранения артефактов ограничен, а учётки для CI
берутся только тестовые.

### Required check

Сделать **Playwright E2E** обязательной проверкой для `main` — отдельный шаг в
Settings → Branches, он требует прав администратора репозитория.
