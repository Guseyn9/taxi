# TEST-E2E-001 — посадка по коду в голосовом заказе

Playwright-прогон полного пользовательского сценария против **живого backend**
(`https://ibronevik.ru/taxi/c/gruzvill/api/v1`). Закрывает дефект
ТЗ-DRIVER-BOARDING-001: после подтверждения кода посадки бэкенд переводил заказ
в `Started`, а интерфейс водителя оставался в режиме «Код посадки».

## Запуск

```bash
cd taxi
npm run test:e2e                              # все тесты
npm run test:e2e -- --project=standard-order  # только А.1.1
npm run test:e2e -- --project=voting-order    # только А.1.2
npm run test:e2e -- --project=driver-boarding # только посадка по коду
npm run test:e2e:report                       # HTML-отчёт последнего прогона
```

Dev-сервер Playwright поднимает сам (`npm start`). Если он уже запущен —
переиспользует; чтобы указать другой адрес, задайте `E2E_APP_URL`.

Первый запуск требует браузера: `npx playwright install chromium`.

## Учётные данные

Тест работает с настоящими учётками — в репозиторий они не попадают. Создайте
`taxi/.env.e2e.local` (он в `.gitignore`) или задайте переменные окружения:

```
E2E_DRIVER_LOGIN=...
E2E_DRIVER_PASSWORD=...
E2E_DRIVER_TYPE=e-mail
E2E_DRIVER2_LOGIN=...
E2E_DRIVER2_PASSWORD=...
E2E_DRIVER2_TYPE=e-mail
E2E_PASSENGER_LOGIN=...
E2E_PASSENGER_PASSWORD=...
E2E_PASSENGER_TYPE=e-mail
E2E_API_BASE=https://ibronevik.ru/taxi/c/gruzvill/api/v1
```

Подойдут те же тестовые аккаунты gruzvill, которыми пользуется
`driver-emulator` (`driver-emulator/config.json`): водитель из `drivers[]` и
пассажир из `orderGenerator.clients[]`. У водителя должна быть привязанная
машина — из неё берётся код посадки.

`E2E_DRIVER2_*` — **второй водитель, отдельная учётка со своей машиной**. Он нужен
только голосованию (TEST-E2E-003): смысл А.1.2 в том, что один заказ одновременно
доступен нескольким водителям, и одной учёткой этот сценарий не воспроизводится.
Тест проверяет, что `E2E_DRIVER2_LOGIN` указывает не на того же пользователя, что
`E2E_DRIVER_LOGIN`, и падает, если учётка одна и та же.

Если `E2E_DRIVER2_*` не заданы, вход второго водителя в проекте `setup`
пропускается, и остальные тесты работают как раньше. Сам голосовой тест при этом
падает — молча пропускать сценарий он не должен.

## Что настоящее, а что нет

Настоящее: frontend, Taxi API, состояние заказа, переходы, обе роли.
**Ни один endpoint сценария не подменяется** — ни создание заказа, ни
`set_performer`, ни `set_arrive_state`, ни `set_start_state`.

Единственный мок — тайлы карты (внешний тайловый сервер к посадке отношения не
имеет, §4 ТЗ).

Что делает браузер: смотрит заказ, откликается, едет, отмечает прибытие, вводит
код и подтверждает. Что делает тест напрямую через API: готовит данные
(пассажир создаёт голосовой заказ и выбирает водителя) и **независимо** от UI
читает состояние заказа для проверок. Redux из теста не трогается, шлюз не
вызывается, backend-команды вместо клика не отправляются.

`?driverEmulator=1` в адресе — штатный переключатель приложения
(`tools/emulatorMode.ts`), без него список заказов водителя принудительно пуст.
Это режим приложения, а не мок API.

## Тесты

| Тест | Что проверяет |
|---|---|
| A | правильный код → backend `Started`, интерфейс `Started`, форма посадки закрылась |
| B | код неверной формы → команда не уходит, заказ остаётся `Arrived`, интерфейс в режиме посадки |
| C | двойное нажатие «Подтвердить» → одно корректное итоговое состояние |
| D | перезагрузка страницы → интерфейс всё ещё `Started`, подтверждение кода не вернулось |

Состояние интерфейса читается атрибутом `data-driver-state` кнопки основного
действия, а не переводом подписи: подписи приходят из конфигурации бэкенда и
зависят от языка, состояние — нет.

## Почему в тесте A есть верхняя граница по времени

Дефект был не в том, что интерфейс **никогда** не догонит бэкенд, а в том, что
он догонял его только следующим опросом списка заказов. Первая версия теста без
границы **проходила на сломанном коде** — это проверено инъекцией регрессии.

Поэтому тест A замеряет, за сколько интерфейс приходит в `Started`, и требует
уложиться в `UI_SYNC_BUDGET_MS` (1.5 с) — заведомо меньше периода опроса
активных заказов (5 с) и отложенного refresh (1.5 с). Уложиться можно только за
счёт локальной синхронизации.

Проверка инъекцией регрессии (полный откат исправления — синхронизация store в
карточке, оптимистичное состояние карты и отметка подтверждённой посадки):

```
Expected: 5   (Started)
Received: 4   (Arrived)
```

То есть тест ловит ровно ту картину, что описана в ТЗ: `Backend = Started`,
`UI = Arrived`.

Откат **только** карточной синхронизации или **только** механизмов карты тест не
ловит — оставшегося пути хватает, чтобы уложиться в бюджет. Точечно каждый
механизм сторожат unit-тесты (`driverBoarding.test.ts`,
`DriverBoardingProjection.test.js`, `driverOrderState.test.ts`).

## Что выяснилось про backend (важно для §16 ТЗ)

На конфигурации `gruzvill`:

1. **Код посадки бэкендом не проверяется.** `set_start_state` с заведомо
   неверным `b_driver_code` возвращает `success` и переводит водителя в
   `c_state = 5`. Проверено напрямую по API.
2. **`b_driver_code` в заказе не возвращается.** Приложение сверяет введённый
   код с `order.b_driver_code` (`tools/driverBoarding.ts`), и когда его нет —
   принимает любой код правильной формы (3–4 цифры).
3. Передача `b_driver_code` в `set_performer` отклоняется («wrong driver code»),
   что совпадает с комментарием в `src/API/order.ts` и безопасным ретраем там же.

Поэтому требование ТЗ «неверный код → `Command = FAILED`, `Backend ≠ Started`»
на этом бэкенде невыполнимо: отвергнуть можно только код неверной **формы**, и
делает это фронтенд. Тест B проверяет ровно эту, настоящую гарантию — и не
имитирует недостающую серверную проверку моками. Валидацию кода на сервере
стоит завести отдельной задачей.

# TEST-E2E-002 — А.1.1, стандартный вызов

Первый сквозной тест на стандартный вызов такси. Он же — каркас для А.1.2
(голосование, реализовано в `voting-order.spec.ts`) и А.1.3 (предложение; пока
не реализовано).

## Запуск

```bash
cd taxi
npm run test:e2e -- --project=standard-order
```

Учётные данные — те же, что у TEST-E2E-001 (раздел выше). Дополнительно нужен
пассажир: проект `setup` теперь входит **обеими** учётками и складывает
`e2e/.auth/driver.json` и `e2e/.auth/passenger.json`.

## Две независимые сессии

```
browser
├── passengerContext (storageState: e2e/.auth/passenger.json) → passengerPage
└── driverContext    (storageState: e2e/.auth/driver.json)    → driverPage
```

Два разных пользователя — два разных контекста. Одной сессией два пользователя
не изображаются.

## Сценарий и проверки

| Шаг | Действие | Проверка |
|---|---|---|
| подготовка | водитель на линии, список активных заказов пассажира очищен, заказ создан через API | — |
| 1 | — | заказ создан: бэкенд отдаёт его по номеру |
| 2 | — | тип **А.1.1**: нет `b_voting`, нет услуги `5`, `b_cars_count ≠ 0` |
| 3 | пассажир открывает `/passenger-order` | заказ виден пассажиру в списке активных |
| 4 | водитель открывает список заказов | доступен **именно этот** заказ (карточка по `b_id`) |
| 5 | водитель жмёт «Взять заказ» | — |
| 6 | — | тип **А.1.1** (вторая опора): водитель сразу `Performer`, а не `Considering` |
| 7 | — | исполнитель ровно один, и это наш водитель |
| 8 | пассажир выбирает заказ | пассажир видит назначенного водителя (`Performer`) |
| 9 | водитель: вкладка «Карта» → «Поехал» | backend и интерфейс водителя в `Arrived`; пассажир видит `Arrived` |
| 10 | водитель: «Приехал» | backend и интерфейс водителя в `Started`; формы кода посадки не было |
| 11 | — | пассажир видит начало поездки (`Started`) |

### Почему тип заказа проверяется дважды

Признаки типа в самом заказе (`b_voting`, услуга `5`, `b_cars_count`) — это то,
как приложение различает три режима (`src/tools/driverOffer.ts`). Проверяются они
по контракту, а не по строке: `b_cars_count = 0` — это «предложение», у
стандартного вызова поле либо отсутствует, либо содержит положительное число
машин; нечисловое значение проверку тоже не проходит.

Оговорка про `b_cars_count`: **на gruzvill этот признак не работает.** Заказ,
созданный с `b_cars_count = 0`, читается обратно как `"1"` — проверено и числом,
и строкой. То есть отличить А.1.3 полями заказа на этой конфигурации нельзя, и
ветка `isOfferOrder` по `b_cars_count` (`src/tools/driverOffer.ts`) здесь не
срабатывает. Сверка контракта в тесте оставлена на случай, если бэкенд начнёт
хранить признак, но опираться в различении типа приходится не на неё.

Сильнее признаков — проверка поведением: после клика «Взять заказ» тест ждёт на
бэкенде именно `Performer`. Голосование и предложение завели бы водителя
кандидатом (`Considering`), и исполнителем его сделал бы только выбор пассажира
(`src/API/order.ts`) — которого в этом сценарии нет. То есть на голосовом заказе
ожидание не дождалось бы `Performer` никогда.

Обе проверки не зависят ни от подписи кнопки, ни от языка интерфейса.

### Что именно проверяется под словом «назначен»

`order.drivers` — это список **записей участия**, а не список исполнителей: у
записи есть и `c_becomed_candidate`, и `c_canceled`, то есть отказавшийся
водитель остаётся в заказе записью с `c_state = Canceled`
(`EBookingDriverState`, `src/types/types.ts`). Проверено на живом бэкенде.

Поэтому тест не требует, чтобы список состоял из одной записи — это была бы
проверка внутреннего устройства бэкенда. Проверяется бизнес-инвариант:

* исполнитель ровно один, и это наш водитель (`c_state === Performer`);
* рядом нет другого водителя, который всё ещё в игре, — то есть в любом
  состоянии, кроме `Canceled`.

## Что настоящее, а что нет

Настоящее: frontend, Taxi API, состояние заказа, переходы FSM, обе роли.
Ни один endpoint сценария не подменяется — ни `set_performer`, ни
`set_arrive_state`, ни `set_start_state`. Единственный мок — тайлы карты.

Через API делается ровно две вещи: **подготовка предусловия** (водитель на
линии, заказ создан) и **независимая от интерфейса проверка** состояния заказа.
Все действия сценария — клики в браузере.

Заказ создаётся тем же набором полей, что собирает форма пассажира для режима
`order` (`src/pages/Passenger/VotingForm.tsx`): без `b_voting`/`b_services`
голосования и без `b_cars_count=0` предложения. `set_confirm_state` не
отправляется — приложение шлёт его только для голосовых заказов.

### Объём теста: создание заказа — предусловие, а не покрытие формы

Решение принято осознанно и зафиксировано здесь, чтобы его не приняли за
упущение: шаг **«пассажир заполнил форму и нажал „Заказать“» этим тестом не
проверяется**. Заказ создаётся через API как fixture, и сценарий начинается с
уже созданного заказа.

Почему так:

* создание заказа из формы — это отдельная содержательная история: выбор точек
  на карте, класс авто, число мест, цена, комментарии, три кнопки режима
  (`Vote` / `Offer` / `Order`). Втащив её в первый сквозной тест, мы получили бы
  тест, который падает то на форме, то на поездке, и по которому непонятно, что
  именно сломалось;
* точки в форме ставятся кнопкой «точка на карте», а адрес к ним подтягивает
  внешний геокодер (Nominatim/HERE, `src/API/index.ts`) — ещё один внешний
  источник нестабильности поверх и без того нестабильного бэкенда;
* тип заказа при этом не остаётся на веру: он проверяется и по полям заказа, и
  по поведению FSM (см. выше).

**Следующий шаг:** отдельный E2E на создание заказа из пассажирской формы —
именно он закроет «пассажир создал заказ через UI». К нему же естественно
отнести проверку выбора режима (`Order` против `Vote` и `Offer`).

## Состояния в интерфейсе

Оба интерфейса отдают состояние числом, а не подписью:

* водитель — `data-driver-state` на кнопке основного действия (`pages/Driver/Map.tsx`);
* пассажир — `data-driver-state` на панели водителя (`pages/Passenger/VotingForm.tsx`).

Подписи приходят из конфигурации бэкенда и зависят от языка, состояние — нет.

## Изоляция и уборка

Заказ помечается `[DRV:<id>]` — механизм самого приложения, по которому водитель
в режиме внешнего эмулятора видит только свои тестовые заказы.

### Что уборка отменяет, а что не трогает

Уборка отменяет **только заказы с тестовыми метками** (`e2e/fixtures/taxiApi.ts`,
`isTestOrder`):

| Метка | Кто ставит |
|---|---|
| `[E2E <label>]` | эти тесты |
| `[DRV:<id>]` | driver-emulator, читается приложением (`src/tools/emulatorMode.ts`) |
| `[CASE] <имя>` | driver-emulator, имя тест-кейса |

Заказ без такой метки уборка **не трогает никогда** — она его пропускает и
называет в логе прогона (`E2E sweep: не тронуто заказов — …`). Это защита от
самой опасной ошибки конфигурации: если в окружении окажется чужой
`E2E_PASSENGER_LOGIN`, тест не отменит настоящие заказы настоящего пассажира.
Полагаться на «учётка ведь тестовая» здесь нечем — это молчаливое
предположение, а не гарантия.

Метка — единственный критерий, и у уборки после прогона он тот же, что у
уборки перед ним. Участие тестового водителя в заказе критерием отмены
сознательно не является: непомеченный заказ — это заказ настоящего пассажира,
и состав его участников прав на отмену уборке не даёт.

Обратная сторона: если на учётке остался мешающий заказ **без** тестовой метки,
уборка его не уберёт и сценарий может из-за него упасть. Такое падение
разбирается по строке `E2E sweep: не тронуто заказов` в логе — и это лучше, чем
незаметно отменить чужой заказ.

### Пагинация

Список активных заказов бэкенд отдаёт порциями (на gruzvill — по 5), причём
параметра смещения у endpoint нет. Обе уборки — и перед прогоном, и после
него (`cancelTestOrders`) — читают список повторно, пока порция приносит хоть
один отменяемый заказ.

Отсюда предел: порция, целиком состоящая из заказов без тестовых меток,
окно списка не сдвигает, и до тестовых заказов за ней уборка не доберётся. В
этом случае пропущенные номера тоже уходят в лог.

## Известная нестабильность: загрузка конфигурации приложения

Приложение при старте тянет конфигурацию отдельным скриптом с сервера
(`src/config.ts`): сначала `GET /api/v1/?cv=` за версией кэша, затем
`https://ibronevik.ru/taxi/cache/data_<config>.js`. Пока конфигурация не
загрузилась, весь интерфейс подменяется экраном «Database is unavailable»
(`src/Routes.tsx`).

**Повторной попытки в приложении нет.** Один сетевой сбой — и страница остаётся
на этом экране навсегда:

* если падает загрузка скрипта — `script.onerror` переводит конфигурацию в
  `Fail`, и это состояние видно в `data-config-status`;
* если не отвечает `?cv=` — промис отклоняется, скрипт вообще не добавляется, и
  приложение навсегда остаётся в `Loading`, без всякого признака ошибки.

Измерено на живом бэкенде: **1 сбой на 25 загрузок страницы** в спокойный период
и серии подряд в периоды деградации (в тех же прогонах бэкенд отдавал `HTTP 502`
и обрывал соединения). Каждая перезагрузка страницы — новая попытка, поэтому
тест сведён к минимуму перезагрузок: вкладка «Карта» открывается кликом по
вкладке, а не переходом по адресу.

Загрузка оболочки — и только она — повторяется из теста перезагрузкой страницы,
до трёх попыток (`e2e/fixtures/appShell.ts`). Это не обход проверок сценария:
ни один его шаг не пропускается, ни одно утверждение о состоянии заказа не
смягчается, а сценарий к этому моменту ещё не начинался — приложение просто не
открылось. Если оболочка не поднялась и с третьего раза, тест падает с явной
причиной, а не с немым таймаутом ожидания элементов, которых на этом экране нет.

Дефект при этом не заминается: каждая такая перезагрузка печатается в лог
прогона строкой `E2E APP BOOT FAILED` и попадает в аннотации теста, так что
видна и в зелёном прогоне. Починка — отдельная задача к приложению (таймаут и
повтор загрузки конфигурации); в этой ветке production-логика не менялась.

## Атрибуты, добавленные в приложение

Только `data-*`, ни строки логики — тот же приём, что уже применён для кнопки

| Файл | Атрибуты |

| `src/Routes.tsx` | `data-testid="app-config-unavailable"`, `data-config-status` |

До этого во всём `src/` было пять `data-testid`, и все — водительские: у
пассажирского интерфейса и у карточки заказа в списке зацепиться за конкретный
заказ было нечем.

Что добавлено голосованием (TEST-E2E-003) и зачем именно атрибуты:

* **строка кандидата и кнопка «Выбрать».** Голосование заканчивается выбором
  пассажира, и выбрать надо конкретного водителя. В разметке кандидата не было
  ни его `u_id`, ни устойчивого селектора, а подпись кнопки приходит из перевода.
* **`data-driver-id` у панели водителя.** ТЗ требует сверить показанного
  пассажиру водителя с назначенным на бэкенде. Имя для этого не годится — оно не
  уникально и приходит из профиля.
* **окно результата действия.** Отклик на голосование подтверждается модальным
  окном, и до карты, пока оно открыто, не добраться. Исход читается атрибутом
  `data-message-status` (`success` / `warning` / `fail`), а не заголовком.

# TEST-E2E-003 — А.1.2, голосование

Сквозной сценарий голосования: один заказ, два водителя, выбор исполнителя
пассажиром.

## Запуск

```bash
cd taxi
npm run test:e2e -- --project=voting-order
```

Нужны все три учётки, включая `E2E_DRIVER2_*` (раздел «Учётные данные»).

## Три независимые сессии

```
browser
├── passengerContext (storageState: e2e/.auth/passenger.json) → passengerPage
├── driver1Context   (storageState: e2e/.auth/driver.json)    → driver1Page
└── driver2Context   (storageState: e2e/.auth/driver2.json)   → driver2Page
```

Общих cookies и localStorage у ролей нет.

| подготовка | оба водителя на линии, тестовые заказы пассажира убраны, заказ создан через API | — |

| 6 | оба водителя жмут «Готов поехать» | приложение подтвердило отклик; на бэкенде оба `Considering` |
| 7 | — | **AC-3**: кандидаты появились, но исполнителя нет и `b_state` не изменился |

| 13 | — | поездку выполняет ровно один водитель — выбранный |

## Чем голосование отличается от А.1.1 в самом тесте

**Заказ создаётся без метки `[DRV:<id>]`.** Метка — механизм изоляции самого
приложения: в режиме внешнего эмулятора водитель видит только свои помеченные
заказы (`state/orders/selectors.ts`, `filterReadyOrdersByTrainingDriver`).
Голосованию нужно ровно обратное. Уборка от этого не страдает: она работает по
метке `[E2E <label>]`, которая остаётся (см. «Что уборка отменяет»).

Проверено на бэкенде: `[DRV:]` — фильтр **клиентский**. В `/drive/now` водителю
приходят и помеченные чужим id заказы; прячет их приложение.

**Заказ создаётся с `b_max_waiting = 900`.** Пассажирский интерфейс доверяет
этому полю только в окне `0 < x ≤ 900` и иначе считает ожидание равным 180 с
(`VotingForm.tsx`, `getChoiceOrderMaxWaitingSeconds`), после чего **сам отменяет
голосовой заказ** по истечении времени. Сценарий из тринадцати проверок в 180 с
не укладывается. 900 — обычное значение поля заказа: не мок, не подмена FSM.
Бэкенд его принимает и возвращает обратно без изменений.

**Выбор исполнителя — клик пассажира, а не вызов API.** Таймерного автовыбора у
приложения нет: исполнителя назначает `chooseCandidate` (`set_performer` с
`performer='1'` и `u_id`), и вызывается он только из кнопки «Выбрать» в списке
откликов. Поэтому шаг 8 сделан кликом, а не `choosePerformer` из фикстуры —
в отличие от TEST-E2E-001, где выбор пассажира был предусловием, а не предметом
проверки.

**Переход `Arrived → Started` идёт через код посадки.** Для голосового заказа
это часть контракта, а не обход: тот же путь проверяет TEST-E2E-001. Код
настоящий, водительский (`boardingCodeOf`).

## Что выяснилось про backend голосования

Замерено зондом на живом gruzvill до написания теста:

| Этап | `b_state` | `drivers[]` |
|---|---|---|
| заказ создан и подтверждён | `1` (Processing) | пусто |
| водитель откликнулся | `1` | `c_state = 1` (Considering) |
| пассажир выбрал водителя | `2` (Approved) | `c_state = 3` (Performer) |
| водитель отметил прибытие | `2` | `c_state = 4` (Arrived) |
| поездка началась | `2` | `c_state = 5` (Started) |

Отсюда две опоры теста: состояние заказа (`b_state`) и состояние участия
(`c_state`) — обе числовые, от языка интерфейса не зависят.

`remaining_lifetime_seconds` в ответе `/drive/get/{id}` **не приходит**, поэтому
оставшееся время голосования тест не проверяет — приложение считает его само от
`b_created` и `b_max_waiting`.

## Состояние проигравшего кандидата

`drivers` — это записи участия, а не список исполнителей: отказавшийся водитель
остаётся в заказе записью. Поэтому тест проверяет не отсутствие записи, а её
состояние: проигравший не `Performer` и находится в одном из двух состояний,
которыми приложение описывает водителя вне поездки, — `Considering` или
`Canceled` (`types/types.ts`, `EBookingDriverState`).

Замерено на gruzvill: после выбора пассажира проигравший остаётся
**`Considering`** — бэкенд его не снимает и не отменяет. Заказ при этом уже
`b_state = 2`, а исполнитель ровно один, поэтому кандидатом он остаётся
формально: в поездку он не попадает, что тест и проверяет отдельно на последнем
шаге.

## Почему карта открывается переходом, а не вкладкой

У А.1.1 водитель нажимает «Взять заказ» и сразу становится исполнителем на той же
странице, поэтому там достаточно переключить вкладку (`switchToDriverMap`).

У голосования путь другой: после отклика приложение само уводит водителя с
карточки заказа (`CardModal.tsx`), а исполнителем он становится позже и **чужим
действием** — выбором пассажира. В этот момент клик по вкладке «Карта» до
основного действия не доводит: страница остаётся на списке, и
`driver-map-primary-action` не появляется. Поэтому карта открывается переходом
(`openDriverMap`) — тем же способом, которым её открывает TEST-E2E-001 для
голосового заказа.

# Общее для всех тестов

## Артефакты при падении

`trace`, `screenshot`, `video` — в `e2e-results/artifacts/`, HTML-отчёт в
`playwright-report/`. Оба каталога в `.gitignore`.

## Изоляция

Каждый прогон создаёт свой заказ, помеченный `[DRV:<id>]` — механизм самого
приложения, по которому водитель в режиме внешнего эмулятора видит только свои
тестовые заказы. После теста заказ отменяется (`afterEach`), аккаунты не
зависают. Подметание зависших заказов ограничено заказами с тестовыми метками —
см. «Изоляция и уборка» выше.

Тесты идут строго по одному (`workers: 1`): они делят одного тестового водителя
и его машину.

## CI

`.github/workflows/e2e.yml` — job **Playwright E2E**, запускается на каждый
Pull Request и на push в `main`. Он выполняет ровно ту же команду, что и
разработчик локально:

```
GitHub Actions → npm ci → playwright install chromium → npm run test:e2e
                                                              │
                                              npm start (localhost:3000)
                                                              │
                                          живой backend gruzvill
```

Отдельной CI-реализации сценария нет: один тестовый код, два способа запуска.
`workers: 1`, `retries: 1` и сбор артефактов приходят из `playwright.config.ts`
по переменной `CI`, которую GitHub выставляет сам, — в workflow они не
дублируются.

### Секреты

Учётные данные в CI берутся только из GitHub Secrets репозитория (Settings →
Secrets and variables → Actions). Ключи те же, что в `taxi/.env.e2e.local`:

```
E2E_DRIVER_LOGIN      E2E_PASSENGER_LOGIN      E2E_API_BASE
E2E_DRIVER_PASSWORD   E2E_PASSENGER_PASSWORD
E2E_DRIVER_TYPE       E2E_PASSENGER_TYPE
```

Аккаунты должны быть **тестовыми**: прогон создаёт настоящие заказы. В коде и в
workflow нет ни одного значения — только `process.env.*`.

PR из форка секретов не получает: там тест упадёт с понятным сообщением из
`fixtures/accounts.ts`. Это не маскируется — `continue-on-error` в workflow нет.

### Очередь

Прогоны выстроены в общую очередь (`concurrency`, без отмены текущего): тесты
делят одного тестового водителя и его машину, и два параллельных прогона ломали
бы состояние заказа друг другу.

### Артефакты и диагностика

Артефакты выгружаются всегда (`playwright-e2e-<run>-<attempt>`, 7 дней):
`taxi/playwright-report/` и `taxi/e2e-results/`. Выгрузка на любом исходе нужна
для §15 ТЗ: если первая попытка упала, а вторая прошла, это должно быть видно в
отчёте, а не спрятано за retry.

При падении в лог job уходит строка `E2E FAILURE DIAGNOSTICS` с `orderId`,
`driverId`, `carId` и состоянием заказа на бэкенде. Если отменить заказ не
удалось — `E2E CLEANUP FAILED: orderId=…`: по этому номеру заказ можно найти и
удалить руками. Токены, пароли и cookie в диагностику не попадают.

`taxi/e2e/.auth/` (там storageState с токеном сессии) в артефакты не выгружается.
Проект `setup` идёт вообще без trace/video/screenshot: он вводит логин и пароль в
форму приложения, а trace хранит само значение `fill()`.

Одного этого мало: к любому упавшему тесту Playwright безусловно прикладывает
`error-context.md` — ARIA-снимок страницы, в котором **и логин, и пароль видны
открытым текстом** (проверено инъекцией падения после ввода). Настройкой это не
отключается, поэтому у `setup` вложение снимает репортёр
`e2e/reporters/stripSetupErrorContext.ts`: он стоит первым в списке, поэтому копия
не доходит ни до HTML-, ни до JSON-отчёта, а файл удаляется с диска. Сообщение об
ошибке и стек при этом остаются целиком. Проверка: сломать селектор кнопки входа в
`auth.setup.ts`, прогнать `npx playwright test --project=setup` и поискать значения
учёток в `e2e-results/` и `playwright-report/` — совпадений быть не должно.

Trace самого сценария содержит сетевой обмен приложения, включая токен сессии
тестового водителя, — поэтому срок хранения артефактов ограничен, а учётки для CI
берутся только тестовые.

### Required check

Сделать **Playwright E2E** обязательной проверкой для `main` — отдельный шаг в
Settings → Branches, он требует прав администратора репозитория.
